## 8. Second-Pass Gap Audit

Organized the same way as v0.3's original audit: what breaks first, or gets skipped silently, if this is handed to Claude Code as-is.

### 8.1 Milo has no physics body — **DECIDED (recommend)** (extends §4.6)

§4.6 gives Milo density, friction, restitution, and angular damping, but never a shape or size. Every overlap check in §4.4, every collision, every stumble-vs-fatal distinction depends on this existing.

**Fix:**
```js
export const MILO_BODY = {
  width: 36,
  height: 72,
  chamfer: 16,       // rounds the rectangle toward a capsule — no clean edges to catch on terrain
};
```
`milo.start.y` in the schema (§4.3) is Milo's **ground-contact point (feet), not his body center** — the physics body is created with its center offset upward by half of `height`. This matches how a level designer thinks about placement ("Milo stands here") rather than requiring center-of-mass math at authoring time. First-guess-to-retune, same status as §4.6's other numbers.

### 8.2 No fixed physics timestep — **DECIDED (recommend)** (extends §4.1, §4.6)

§11's Fair Physics Principles want physics that's predictable and non-random-feeling. Matter.js stepped against a variable frame delta resolves differently on a fast device than a throttled one — the opposite of predictable, and it means two players can draw the identical stroke and get different outcomes for reasons that have nothing to do with the puzzle.

**Fix:** fixed timestep with an accumulator, decoupled from render rate.
```js
const PHYSICS_DT = 1000 / 60;   // fixed, regardless of display refresh rate
const MAX_STEPS_PER_FRAME = 5;  // caps catch-up after a tab was backgrounded — prevents a stall from trying to simulate minutes of physics in one frame
```
Accumulate real elapsed time each RAF tick; call `Engine.update(engine, PHYSICS_DT)` in a loop until the accumulator drops below one step, carrying any remainder forward. Render always draws the latest resolved state — interpolation between physics steps is a nice-to-have, not required for a puzzle game at this scale.

### 8.3 Nothing guarantees the puzzle fits in one view — **DECIDED (recommend)** (extends §4.2)

This is a one-shot drawing game — the player has to see the entire problem to commit to a single stroke. §4.2 fixes world height and bounds puzzle geometry to a safe column, but never states that the full level must be visible with no camera movement. Left implicit, there's a real chance a scrolling or follow-camera gets built by default, which breaks the premise outright.

**Fix:** camera is static per level, for the whole game, not just Phase 0 — no pan, scroll, zoom, or follow. This is a hard constraint on level geometry, not a rendering preference: every level's Milo path, hazards, and goal must sit within the safe column and world-height bounds already defined in §4.2. Worth adding a level-load assertion that warns if any object's coordinates fall outside the renderable bounds, the same spirit as the drawing pipeline's own reject conditions in §4.4.

### 8.4 Near-miss has no trigger definition — **DECIDED (recommend)** (parallel to §2.5/§4.5)

One of Milo's eight named animation states, and nothing defines what counts as one. Same category of gap as §2.5's "stuck" — a named state with no measurable rule either never fires or fires unpredictably.

**Fix:** each physics step, track the minimum observed distance between Milo's body and each hazard's body over the course of the run. At run end, for any hazard where that minimum was under **30 units** and no collision with it occurred, and the run ended in success, fire a `near-miss` event carrying the hazard's id and the measured distance. Gated on a successful run specifically — a near-miss on the way to dying somewhere else isn't a moment worth marking. Fires once per hazard, not continuously.

### 8.5 Phase 0 never exercises the closed-shape path — **DECIDED (recommend)** (extends §4.9)

§4.4 splits stroke classification into two real branches: open chain and closed polygon. The closed branch is what makes the cradle/CATCH mechanic possible, and it carries the harder edge case (self-intersecting shapes falling back to open-chain). None of A1, A2, or A3 require it — A1 says explicitly the solution can be open or closed, A2 is a bridge, A3 is an angled deflector, both inherently open. Phase 0 could pass clean with that entire branch never having executed once.

**Fix — add a fourth Phase 0 level, checked against the spec's own numbers rather than sketched by eye:**

Running Milo's fall from the ledge at his own spec'd walk speed (220 units/s, §4.3) under the spec's own gravity (1800 units/s², §4.6), uncaught: he passes y=1000 at x≈354, y=1050 at x≈366, and hits the y=1250 pit floor — death — at x≈406. That number matters: it means any catch geometry sitting past roughly x=406 is irrelevant to the *catch* itself, it can only ever serve as runway after a successful catch. A bowl guessed at x=300–500 looks reasonable on paper and is wrong by about half its width once you run the numbers.

**A4 — CATCH.** Milo starts at x=100, y=800, on a raised ledge. Ground ends at x=250 — beyond it, open air down to a pit floor at y=1250 (falling = the same fall-failure rule as A2). Goal at x=620, y=1080, on a lower platform. Intended solution: a closed bowl whose catching surface begins by roughly x=310–320 — comfortably ahead of the x≈354 point where an uncaught Milo is only just reaching y=1000 — with its low point around y=1080–1100 near x≈380–400, inside the real fall corridor and with genuine margin before the x≈406 death line. The bowl's right edge extends on to roughly x=480–500 as a landing runway, gently sloped toward the goal rather than flat.

One real design trap worth naming regardless of the exact numbers: the bowl can't be a fully sealed container, or Milo gets caught and never leaves, tripping the stuck-timer (§4.5) instead of succeeding. The goal-facing side needs to stay open or gently tilted so a correct catch also gets him moving again. Tests whether the closed-shape classification path produces a stable catch rather than clipping through or bouncing out unpredictably — this is the level that actually validates §4.4's harder branch, which the original three don't. First-guess-to-retune status, same as §4.6, but now first-guess against a real trajectory instead of against nothing.

### 8.6 Drawing interruption isn't specified — **DECIDED (recommend)** (extends §4.4)

Two mobile-relevant edge cases §4.4 doesn't address: the pointer leaving the canvas mid-stroke, and a second touch point appearing mid-draw.

**Fix:** pointer-leaves-canvas is treated as an implicit release — whatever was captured up to that point runs through the same validation in §4.4 (minimum length, doesn't overlap Milo, etc.) rather than being silently discarded, which would feel arbitrary given how much weight Fair Physics Principles puts on not punishing the player for things outside their control. Multi-touch: lock to the first pointer identifier at stroke start, ignore every other touch point until that stroke ends in release or rejection.

### 8.7 No feedback for approaching the stroke limit — **DECIDED (recommend)** (extends §4.3, §4.4)

`drawing.maxLength` (§4.3) is enforced in §4.4's reject logic, but nothing tells the player they're approaching it while they're still drawing. Hitting an invisible wall mid-stroke is exactly the kind of surprise the release-time overlap rule in §4.4 was written to prevent for a different case.

**Fix:** compute `remainingLength = maxLength − currentPathLength` on every sampled point during drawing and expose it to `render.js`. The actual visual treatment (a depleting bar, the stroke changing opacity as it nears the limit) is a Phase 1 decision — Phase 0 just needs the value computed and available every frame, not a finished look.

### 8.8 One thing checked and ruled out

Worth naming even though it isn't a fix: whether §4.4's simplification (Douglas-Peucker, ~3-unit tolerance) could distort the angle of a hand-drawn ramp enough to matter for A3's 30–40° redirect solution, since real hands don't draw perfectly straight lines. Simulated a noisy hand-drawn stroke at 30°, 35°, and 40° and ran it through the actual algorithm at the spec's tolerance: the overall angle survived exactly, in every trial, because Douglas-Peucker never moves the first or last point of a stroke — it only removes redundant points in between. A near-straight 140-unit stroke collapsed to two points every time, which is the correct outcome for a deflector, not a bug. Not a gap. Included so the question doesn't sit unanswered.

## 9. Additions — for after Phase 0 passes

Not gaps. These don't block Phase 0 and shouldn't be built before it — same "no art budget" discipline v0.3 already applies to itself in §1. Listed now so they're decided in the spec rather than invented ad hoc later.

**Near-miss payoff.** Once §8.4's trigger exists, it's worth a small reaction, not just a flag in code — a brief accent-colored highlight around Milo at the moment it fires. Explicitly deferred past Phase 0.

**Failure slow-motion — DECIDED (recommend).** The Spine (§1) says failure should be instant to *understand*, not just instant to retry. Right now understanding depends entirely on watching it happen once, in real time. On failure detection, drop physics and render timescale to roughly 20% for about 300ms before cutting to the retry screen — long enough to see what actually happened, short enough not to fight the instant-retry goal.

**Audio event map — DECIDED (recommend).** §2.8 correctly defers audio *sourcing*. The event map underneath it isn't a sourcing question: stroke release/solidify, hazard collision, success, stuck-timeout, near-miss, UI taps. Stub all of these now with simple synthesized tones, the same move that let Poof Poof ship real audio hooks before any final track existed — sourcing becomes a swap later, not new plumbing.

**`prefers-reduced-motion` — DECIDED (recommend).** Check `window.matchMedia('(prefers-reduced-motion: reduce)')` once at boot and store the result as a flag that the slow-motion effect above, and any future camera shake or particle work, checks before playing. This landed on Poof Poof's list as a retrofit after the fact. Building it in now costs one line.
