# BRO, YOU'RE COOKED. — Spine & Build-Ready Spec (v0.3)

**What this document is:** v0.2 was the design bible — the thinking, the market case, the philosophy. It's genuinely good on *why* and *what*. It is not yet buildable, because it deliberately leaves the *how* open ("OPEN," "HYPOTHESIS," "DO NOT BUILD YET" appear dozens of times, by design).

This document does three things:

1. **The Spine** — the game with all the padding removed. One page. If everything else got deleted, this is what would have to survive.
2. **Gap Audit** — every place v0.2 either left a hole or hand-waved something Claude Code cannot code against as written. Each gap gets a proposed fix, not just a flag.
3. **Rebuilt Spec** — the concrete decisions, numbers, schema, and file layout Claude Code needs to start Phase 0 today.

Where I made a call, it's marked **DECIDED (recommend)** — you can override any of these in one sentence. Where only you can make the call, it's marked **NEEDS YOU**.

---

## 1. THE SPINE

Strip everything else away and this is the game:

- A character (Milo) walks automatically toward a visible goal.
- Something in his path will kill him.
- The player gets **one drawn stroke**, once, before the run plays out.
- The stroke becomes a real physical object the instant it's released.
- Physics runs. Milo lives or dies. Nothing else happens during that window — no second chance, no button presses.
- Failure is instant to understand and instant to retry.

That's it. Everything else in v0.2 — worlds, stars, monetization, comedy, portfolio strategy — is in service of making *that specific eight-second moment* work. If that moment isn't fun with a triangle standing in for Milo and a grey box standing in for a boulder, no amount of art or level count fixes it. The doc says this itself in section 65 and I'm holding you to it: **Phase 0 has no art budget.**

## 2. GAP AUDIT

Organized by what breaks first if you hand v0.2 to Claude Code as-is.

### 2.1 The data schema can't express the game's own marketing example

Section 40's level schema has no `id` field on any object, and no way for one object to reference another. But section 83's own headline example — *truck hits switch, gate opens, Milo walks through* — requires exactly that: a switch that knows which gate it opens. Level 8 (chain reaction) and half the "verb" list in section 17 (TRIGGER, REDIRECT-into-something) are unbuildable against the schema as written.

**Fix:** every object gets an `id`. Trigger-capable objects carry a `triggers: ["targetId"]` array. See §4.3 for the corrected schema. This isn't a nice-to-have — without it, the game's own signature moment can't be built.

### 2.2 "Canvas/WebGL" and "lightweight 2D physics" are not decisions

Section 73 lists rendering as "Canvas/WebGL" and physics as "lightweight 2D physics," which reads as a decision but is actually two open questions with real consequences: WebGL adds real complexity and payload for a hand-drawn 2D comic game that doesn't need shaders or 3D. And "lightweight 2D physics" doesn't say whether you're hand-rolling a rigid-body solver or using a library — and hand-rolling one that satisfies section 11's "Fair Physics Principles" (predictable, deterministic, non-random-feeling) is a multi-week project prone to exactly the instability those principles are trying to prevent.

**Fix (§4.1):** Canvas 2D, not WebGL. Matter.js for physics, vendored locally (no CDN, matches the closed-sandbox rule in section 78). This is the one recommendation in this document worth your explicit yes — everything else follows your own existing patterns, this one adds a dependency you haven't used before.

### 2.3 The responsive strategy in section 48 is a wish, not a mechanism

Section 48 says landscape should "expand horizontally while preserving puzzle relationships" — correct instinct, no implementation. I already watched this exact gap bite Poof Poof: that game's canvas is a fixed pixel size that gets scaled down to fit, which means on a real phone it letterboxes instead of filling the screen. If BRO ships with the same non-answer, it'll have the same problem, except worse, because this game's world is bigger than one grid.

**Fix (§4.2):** fixed world *height*, variable world *width* computed from the live viewport ratio, with puzzle-critical geometry kept inside a guaranteed-visible center column. Concrete numbers below.

### 2.4 Q4/Q5 (does the line collide with Milo, can you draw over existing geometry) need a Phase-0 default, not a permanent "open"

These are marked open in section 94 with a half-answer ("probably yes, but forgiving"). Claude Code can't ship "probably." A concrete default is needed even if you change it after playtesting.

**Fix (§4.4):** the stroke *does* collide with Milo once physics starts, but a stroke can't be released if it overlaps Milo's current position at release time — promoting section 9.4's optional per-level rule to an always-on baseline. That single rule kills the "I accidentally drew through my own guy and killed him" complaint before it exists, without weakening the physics anywhere else.

### 2.5 "Stuck" failure (section 14) has no detection mechanism

The doc lists "Milo becomes trapped beyond a defined recovery threshold" as a failure condition but never defines the threshold or how it's measured. Without a rule, this either never fires (soft-lock — level never ends) or fires unpredictably (feels unfair, violates section 11 Rule 2).

**Fix (§4.5):** a concrete velocity-and-time-based stuck timer.

### 2.6 No starting physics numbers anywhere

Section 10.3 correctly says *don't expose materials to the player*, but internally, Claude Code still needs a first density/friction/restitution/gravity value to write code against. Nothing in v0.2 gives one — not even a placeholder.

**Fix (§4.6):** starting constants, explicitly labeled as first-guess-to-retune, not final.

### 2.7 Milo needs actual character art, and nobody has said who makes it

This is the biggest real gap in the whole document, and it's a resourcing question, not a design one. Section 7.2 requires eight animation states (idle, run, stumble, fall, impact, near-miss, victory, defeat). Poof Poof got away with zero art — every fruit is a code-drawn circle. Milo cannot be a code-drawn circle and still deliver the "comically unlucky little guy" fantasy the whole brand personality rests on. Section 44 also explicitly flags "obvious AI-generated art" as a Playables certification risk, which narrows your options.

**This is flagged NEEDS YOU below (§5) — Phase 0 doesn't need the answer yet, but Phase 1 (vertical slice) can't start without it, so it's worth deciding in parallel with coding, not after.**

### 2.8 Audio has no sourcing plan

"Small local assets" (section 73) isn't a plan. Section 63 explicitly warns against copyrighted music. Same category of gap as art — doesn't block Phase 0, does block Phase 1.

### 2.9 Legal title clearance is listed as open with no next action

Section 5.4 and 102 both flag it and stop there. It's a cheap, fast check — worth doing now, in parallel, precisely so it's *not* a blocker later.

### 2.10 Scope discipline: which world is actually in v1

Section 24 lists ten worlds as "long-term expansion, not V1 commitments" — good — but nothing in the doc says which single world Claude Code should actually build first. Leaving that implicit invites scope creep the moment content production starts.

**Fix:** World 1 (Backyard Chaos) only, for everything through Phase 2. Nothing else gets touched until retention on World 1 is proven, per section 71's own phase gates.

## 3. WHAT WAS ALREADY RIGHT (not touching this)

No bluffing the other direction: large parts of v0.2 don't need rebuilding.

- The one-stroke rule, Milo's automatic movement, and "player changes the environment, not Milo directly" — this is the actual differentiated idea, and it's sound. Keep it exactly as written.
- The state machine in section 74 is already concrete enough to code against directly.
- The kill criteria (section 69) and phase gates (section 71) are the right discipline — a lot of solo devs skip this and it's why their prototypes never get evaluated honestly. Don't cut it for speed.

## 4. REBUILT SPEC — LOCKED FOR PHASE 0

### 4.1 Tech stack — **DECIDED (recommend)**

- Vanilla JS, ES modules, no bundler, no framework — same pattern as Poof Poof, same reason: it's what you already have a working Claude Code loop for.
- Rendering: **Canvas 2D**, not WebGL.
- Physics: **Matter.js**, vendored as a local file (`vendor/matter.min.js`, ~95KB minified) — no CDN, so it works inside a closed sandbox with no network access.
- Everything else (drawing capture, level data, UI overlays) is hand-written, same as Poof Poof.

### 4.2 Coordinate system & responsive strategy — **DECIDED (recommend)**

- World has a **fixed logical height of 1280 units**. Width is computed at runtime from the real viewport aspect ratio (portrait phone gets a narrower world, landscape/square gets a wider one).
- Puzzle-critical objects (Milo's path, hazards, goal) stay inside a guaranteed **720-unit-wide center column**, regardless of actual world width. Extra width beyond that column is background/environment only — never puzzle geometry. This is the concrete version of section 48's "expand horizontally without changing the puzzle."
- Canvas backing store = CSS pixel size × `devicePixelRatio`, capped at 2×, recalculated on resize.

### 4.3 Level data schema (fixes §2.1)

```json
{
  "id": "backyard-01",
  "world": "backyard",
  "milo": { "start": { "x": 100, "y": 1080 }, "speed": 220 },
  "goal": { "id": "goal", "x": 620, "y": 1080, "w": 80, "h": 140 },
  "objects": [
    { "id": "boulder1", "type": "boulder", "x": 360, "y": 200, "radius": 40,
      "density": 0.03, "restitution": 0.2 },
    { "id": "switch1", "type": "switch", "x": 500, "y": 1180, "triggers": ["gate1"] },
    { "id": "gate1", "type": "gate", "x": 620, "y": 960, "closed": true }
  ],
  "hazards": [],
  "drawing": { "maxLength": 900, "denyZones": [], "requiredAnchorZones": [] },
  "rating": { "twoStarLength": 620, "threeStarLength": 420 }
}
```

Every object that matters has an `id`. Anything that can cause something else to happen carries `triggers`. This is the minimum needed to build the chain-reaction levels the design bible itself uses as its headline example.

### 4.4 Drawing pipeline (fixes §2.2, §2.4)

1. Sample pointer position on a fixed interval (~16ms), not on every raw event.
2. Simplify the sampled path (Douglas-Peucker, ~3-unit tolerance) to cut point count before it becomes physics geometry.
3. **Reject** the stroke (snap back to drawing state, no physics created) if: fewer than 2 points survive simplification, OR total length is under a minimum (~20 units — kills the "accidental tap" edge case from section 75), OR the stroke overlaps Milo's current position at release.
4. **Classify** the simplified path:
   - Start and end points within ~24 units of each other → **closed shape** → filled polygon body (this is what makes a "cradle" / CATCH level possible — you can draw a bowl).
   - Otherwise → **open chain** → sequence of thin rectangular segments (fixed 14-unit thickness) welded at each joint into one compound body.
   - Self-intersecting closed shapes fall back to open-chain treatment for V1 — reliable polygon triangulation of arbitrary self-intersecting strokes is a rabbit hole not worth Phase 0 budget.
5. Once classified, hand the geometry to Matter.js as a static-until-release, then dynamic-on-release body.

### 4.5 Stuck detection (fixes §2.5)

Every physics step: if Milo's speed stays under a small threshold for more than **3 seconds**, and he isn't touching the goal, and it's been more than 0.5s since his last collision (so a normal landing-and-settling moment doesn't falsely trigger it) → fire failure with reason `"stuck"`. Starting numbers, not final — this is exactly the kind of thing Phase 0 playtesting exists to correct.

### 4.6 Starting physics constants (fixes §2.6)

All in `constants.js`, all explicitly first-guess:

```js
export const GRAVITY_Y = 1800;          // world units / s^2

export const LINE = { density: 0.02, friction: 0.6, restitution: 0.05, thickness: 14 };
export const MILO  = { density: 0.01, friction: 0.3, restitution: 0.1, angularDamping: 0.9 };
```

Restitution near zero on the drawn line on purpose — for V1 it should read as *solid terrain*, not a trampoline. A bouncier "rubber" material is a real future idea (section 26) but not a V1 decision.

### 4.7 File architecture

Mirrors the Poof Poof module split — same boundaries, same reason Poof Poof's split worked (each file owns one concern, physics/state/render never reach into each other directly):

```
index.html
css/style.css
vendor/matter.min.js
js/constants.js    — every tunable number, nothing else
js/state.js        — the section-74 state machine, screen transitions
js/levels.js        — level data + loader
js/drawing.js       — stroke capture → simplify → validate → classify
js/bodyFactory.js  — classified stroke → Matter.js body
js/physics.js       — Matter.js engine setup, step, trigger wiring (switch → gate)
js/milo.js          — Milo entity: auto-movement, stumble/react state, stuck timer
js/render.js        — draws world + HUD each frame
js/input.js          — pointer events → drawing.js (unified mouse/touch)
js/ui.js             — DOM overlay screens (menu, result, retry) — same pattern as Poof Poof's shop.js
js/storage.js        — save/load, SDK-first with try/catch fallback, never raw unguarded localStorage
js/sdk.js            — Playables lifecycle stub: gameReady/firstFrameReady/pause/mute, safely a no-op outside Playables so it still runs in a plain browser tab during dev
js/main.js           — boot, RAF loop, wires everything together
```

### 4.8 Platform/SDK requirements (carried forward, not re-derived)

Same platform, same rules I already confirmed against Poof Poof — building them in from day one instead of retrofitting them:

- Call the ready-signal lifecycle hooks at the correct point from the start, not bolted on later.
- `storage.js` is SDK-first with a try/catch fallback — never a bare `localStorage.getItem` with no guard. (This exact bug is what's currently blocking Poof Poof's certification — no reason to build it twice.)
- Pause/mute wired directly into the RAF loop from the first commit.
- **Caveat, same as before:** exact SDK method names and lifecycle timing should come from Google's own Playables developer docs once you have access, not from this document or from third-party guides. The *shape* of the requirement is solid; the literal function names aren't guaranteed accurate.

### 4.9 Phase 0 — the three levels, with real numbers

Using the schema in §4.3, world height 1280, safe column 720 units wide:

**A1 — WALL.** Milo starts at x=100. A ball (`type: "boulder"`, radius 30, restitution 0.3) sits at x=400, y=100, and will roll/fall into his path. Goal at x=620. Intended solution: a short vertical wall (closed or open chain, doesn't matter) between x≈380–420. Tests: does the player understand "draw = block" with zero instruction.

**A2 — GAP.** Ground has a physical break between x=300 and x=500 (a pit — falling through it is a failure trigger, not a wall). Milo starts at x=100, goal at x=620. Intended solution: a bridge — a mostly-flat open chain spanning x≈290–510. Tests: does the player understand "draw = terrain."

**A3 — REDIRECT.** A boulder (radius 40, restitution 0.2) falls from directly above Milo's path at x=400 — blocking it flat-on just stops it in his way, doesn't save him. Intended solution: an angled chain (~30–40°) that deflects the boulder sideways, off Milo's line, before he reaches it. Tests: whether the physics produces a real "aha" rather than just "block harder."

Build these three, in this order, before anything else — including before final art, before the menu screen looks nice, before stars exist. Section 67's five gates are the actual acceptance test, not "does it run without crashing."

## 5. WHAT'S STILL GENUINELY YOURS TO DECIDE

Engineering judgment can't close these — they're creative or business calls:

1. **Milo's art pipeline** — hand-drawn by you/a contractor, or AI-assisted-then-hand-cleaned (given section 44's own warning about "obvious AI-generated art" being a certification risk, "AI-assisted" and "AI-obvious" are not the same thing, but it needs a real decision and a real process, not a placeholder). Doesn't block Phase 0 — the three prototype levels use a triangle or box for Milo, deliberately. Does block Phase 1.
2. **Audio sourcing** — cleared SFX library vs. original composition. Same timing: not a Phase 0 blocker.
3. **Matter.js as the physics dependency** — the one engineering call in this document that's a real judgment call rather than a mechanical fix. I'm confident in it, but it's the one line worth you explicitly saying yes to before Claude Code writes physics.js.
4. **Title legal clearance** — a real search, not a vibe check. Cheap to do now, expensive to discover late.
5. Ad cadence, world order beyond World 1, exact visual style — all correctly deferred by v0.2 itself, and correctly not needed for Phase 0.

## 6. WHAT HAPPENS NEXT

Phase 0, in build order, matches section 104's own sequencing:

1. Boot skeleton: `index.html` + `main.js` + RAF loop + state machine, no physics yet — a triangle that stands still on a static background.
2. Wire in Matter.js: static ground, static Milo-placeholder, verify the engine steps and renders.
3. Drawing pipeline: capture → simplify → classify → body — test by drawing on an empty level and watching shapes fall and settle correctly, before Milo or hazards exist at all.
4. Milo's auto-movement toward a goal, no hazards yet — confirm he walks, reaches the goal, and the level completes.
5. Build A1, A2, A3 exactly as specified in §4.9.
6. Run section 67's five gates on a real person who hasn't seen this document. Their reaction is the actual verdict — not whether the code runs clean.

That's the plan Claude Code can execute against starting now.
